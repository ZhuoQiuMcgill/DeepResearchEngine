# Platform and EBD baseline acceptance

Status: acceptance design only. No runtime or generated report exists yet.
PM owns this workflow and final audit; module teams own their implementation
and module verification as assigned in `missions.md`. Runtime work and live
API calls wait for the authorized phase transition.

## Exact requested end state

Deliver the complete four-module runnable platform and at least one full
report generated by a simple baseline through those modules for the exact
question `What is EBD (Environment Based Design)`. Use the actual DeepSeek
V4.1 Flash profile (`deepseek-flash`), disable provider/internal search by
the rendered system instruction and supported request controls, and use only
registered platform tools for discovery/retrieval. A design, isolated tool
experiment, partial answer or mock report does not complete this objective.

## Minimal baseline workflow

The application uses one flat research agent; child scheduling is unnecessary
for this question. The full platform still must pass child/binding checks.

1. Open Engine through Connections. It starts real Storage/control recording
   and supplies scoped module bindings. Register one bounded AgentDefinition
   with the exact question as input, the selected named DeepSeek profile,
   output contract and only `web.search`, `web.fetch`, `document.read`.
2. Agent instructions define a finite research plan: discover relevant
   Environment Based Design sources, prefer primary scholarly/institutional
   material, fetch selected sources, read immutable snapshots, and produce
   a complete explanatory report with traceable citations. Do not seed it
   with an existing EBD explanation or report. Disambiguate the target term
   from other uses of EBD based on the fetched evidence.
3. Engine.run_agent executes Container's real provider/tool loop. It must
   perform genuine discovery, fetch and saved reads through the CLI interface.
   Named backend failures remain visible. Unsupported/blocked source access
   does not become fabricated evidence. Bound all model/tool/cleanup work.
4. Fetch success requires validated worker preparation, complete READY
   SnapshotStore receipt and acknowledged lifecycle outcome. Cite content
   established by saved `document.read` slices, not discovery snippets.
5. The actual model generates the complete final report. Preserve its bytes;
   PM may rerun for a demonstrated substantive failure, but may not replace
   the report with a manually authored answer or substitute another model.
6. Runtime persists the exact final model-visible report and validated output
   through normal scoped Storage before cleanup and agent.finished. AgentResult
   returns their immutable refs and the obtained terminal receipt. Use a fresh
   authorized host/result-access binding to read/export those bytes and publish
   a citation manifest and terminal CheckpointStore checkpoint. Retain task/definition/
   configuration/run identities, flat plan, source refs, report ref, output
   status and recording status. Publication events are automatic.
7. Close Engine in the defined order, reopen with newly authorized bindings,
   retrieve identical report bytes/checkpoint/cited slices and paginate its
   committed activities. Verification cannot refetch sources or regenerate
   the report to conceal a durability failure.

The post-run binding has its own bounded deadline and explicit current grants;
it does not revive expired agent authority or use record_cleanup for business
writes. Diagnostic preservation of a failed run cannot convert it into success.

The baseline imports public Engine/contracts and consumes scoped Storage
through bindings. It contains no direct model SDK/HTTP request, DDGS call,
HTML/PDF parser, subprocess launcher or alternate snapshot/database writer.
The application owns research instructions/sequence; modules own execution.
An export reads the saved artifact through Storage rather than substituting
the model text from an unrelated buffer.

## Search policy and model evidence

The rendered system instruction explicitly says: do not use internal,
provider-hosted or implicit web search; research only through the registered
platform function tools; fetch and read source evidence before citing it.
The actual request contains only the approved function tools and supported
profile settings. Use an official search-disable control if available; do
not send invented parameters or treat disabling thinking as disabling search.
This implements the user's permitted system-instruction method. Provider
internals inaccessible to the client are not independently observable.

Store a sanitized rendered-request audit: requested model/profile/revisions,
safe endpoint identity, system instruction or immutable instruction reference,
function tool names/schemas, settings, request digest and provider-reported
model/request/response IDs when available. Record unknown metadata honestly.
No auth headers, keys, env values or unsanitized diagnostic bodies. Verify
the selected profile against current official model/account evidence during
authorized acceptance and never silently substitute another model.

## Deliverables and proof

Storage is the authoritative deliverable source. A future export may use
ignored `local/runs/<run_id>/` for reviewable copies; exact actual paths must
be reported after the run, not claimed in advance.

| Deliverable | Required evidence |
| --- | --- |
| Full report | Actual model-generated final output saved as a readable Markdown artifact, successful validated AgentResult and matching close/reopen bytes |
| Citation manifest | Every report citation maps to source URL, store-qualified snapshot ref, extraction revision/hash and exact line/page range established by saved reads |
| Request audit | Actual DeepSeek model/profile and rendered platform-only search policy/function tools; safe provider IDs and metadata |
| Execution trace | Durable binding/start/terminal records; paired model/tool intents and outcomes; provider-native call pairing; snapshot/report/checkpoint commit receipts |
| Terminal checkpoint | Exact task/run/definition/config/plan/source/report references and complete recording, readable after reopen |
| Acceptance record | Actual commands, results, hashes, limitations and requirement-by-requirement completion classification |

PM checks the complete report for a clear answer to the requested term, its
source-supported definition and method, practical explanation/examples where
evidence supports them, and material limitations/uncertainty. Validate each
citation target and the core claims against the retained slices. A polished
answer with missing or unrelated citations is not successful acceptance.

## Full platform audit

The baseline proves this real workflow; it does not alone prove every module
requirement. Audit the following independently with the owning teams:

| Requirement | Owner and authoritative proof |
| --- | --- |
| Same uv/Python 3.11+ platform | PM: committed manifest/lockfile, locked sync/run and actual interpreter/dependency evidence |
| Agent definitions/runtime | Container: documented runnable entry points; real validation, model/tool loop, limits and lifecycle results |
| DeepSeek and GPT-6-Luna APIs | Container: real bounded tool conversations, native continuation and actual request/response evidence for both |
| Local vLLM Qwen connector | Container: complete configurable implementation/deployment manifest and local interface checks; live verification explicitly pending because no deployment exists here |
| CLI search/fetch/read | Toolset: real subprocess/JSON operation, named backend research availability and URL fidelity, HTML/plain-text/text-PDF provenance and immutable reads |
| Resource/process behavior | Toolset: encoded max-fit/oversize/escaped inputs, PDF expansion/peak-memory evidence, deadline/cancel/crash/overflow and actual worker/descendant cleanup |
| Storage and automatic hooks | Storage/Container: verified startup settings, durable intent-before-dispatch and publication events; successful state/artifact/snapshot/checkpoint close/reopen |
| Permission and CAS isolation | Storage/Connections: real scoped denial/version conflicts, references without implicit authority, child export and shared-lineage limit evidence |
| Retry/uncertainty/recovery | Storage/Container/Connections: exact-ID append/write delivery reconciliation, no external replay, interrupted admitted writes/leases settled or explicitly unknown |
| Connections/standalone/children | Connections: real module binding, dotenv/lazy-profile errors, same recorded standalone helper, permitted invocation and ordered cancellation/shutdown |
| Module ownership and handoff | PM/leaders: source boundaries, runnable consumer docs, completed owned tests and sequential reviewed Git contribution |

## Completion decision

For each row, classify actual evidence as proven, contradicted, incomplete,
missing or too weak. Unresolved publication/recording is incomplete even if a
model returned text. Design prose, mocked provider responses and isolated
search trials cannot prove runtime integration. Re-run only when changes or
unresolved failures justify it. Preserve the user-approved local-deployment
limitation, rather than claiming Qwen was live-tested.

Only after the full platform audit and complete saved baseline report pass
does PM mark the goal complete. Record actual report/trace paths, key passed
checks and remaining explicit deployment limits in the final handoff.
